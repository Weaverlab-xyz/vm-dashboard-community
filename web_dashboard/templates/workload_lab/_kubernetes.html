Nothing here is built yet

This tab is the argument for a pattern, not a feature. There is no build button, and the three playbooks it describes do not exist. The reasoning, including what would have to be settled first, is in the design note.

The SPIRE tab mints audience-scoped JWT-SVIDs, and nothing in this dashboard presents one to anything. This is the relying party worth picking: a workload reaches the Kubernetes API with a token that lives for minutes and is written to no disk and no vault, anywhere.

How it works

Two upstream projects in the SPIFFE org, one on each side of the connection.

  1. A SPIRE agent on the workload's host attests it, the same way any SPIFFE workload is attested.
  2. The workload asks the Workload API for a JWT-SVID with audience k8s.
  3. kubectl gets that token from an exec credential plugin and sends it as the bearer token.
  4. The API server validates it as an ordinary OIDC token against the SPIRE OIDC Discovery Provider, and RBAC binds the SPIFFE ID.

The client half — the whole kubeconfig user

user:
  exec:
    apiVersion: "client.authentication.k8s.io/v1"
    command: "k8s-spiffe-workload-jwt-exec-auth"
    interactiveMode: Never

spiffe/k8s-spiffe-workload-jwt-exec-auth · reads the Workload API socket; audience from SPIFFE_JWT_AUDIENCE.

The server half — kube-apiserver structured authentication

jwt:
- issuer:
    url: https://oidc-discovery.example.org
    audiences:
    - k8s

spiffe/k8s-spiffe-workload-auth-config · injects the SPIFFE trust bundle as certificateAuthority, loaded with --authentication-config.

Against the path that is already built

This would not replace ServiceAccount token rotation. The two answer different questions, and the interesting claim is what each one still leaves lying around.

Bound-mode SA token (built) JWT-SVID over the Workload API (not built)
Where the credential rests Password Safe, and PRA Vault via the synced account Nowhere — process memory, for minutes
Who can replay it Anyone who can retrieve it from either vault A caller on the attested workload's own machine
What binds it The ServiceAccount's uid claim Node and workload attestation
EKS / AKS / GKE Yes No — needs a self-managed API server
Governed as an inventory row Yes No — there is no credential to govern
The built path is on the Kubernetes page — a cluster's Password Safe token rotation action — with its reasoning in its own design note.

What it would need

A k3s cluster, not a managed one. --authentication-config is a kube-apiserver flag, and EKS, AKS and GKE do not expose it. k3s takes it through kube-apiserver-arg, and the k3s/ playbooks already stand a server up and emit a registration-ready kubeconfig. That limitation is the pattern's reach: a customer running only managed clusters cannot adopt it.

Three playbooks that do not exist yet — the OIDC Discovery Provider beside the SPIRE server, a SPIRE agent on the k3s node (the lab installs the server only), and the API server's authentication config plus an RBAC binding whose subject is the SPIFFE ID.

Structured Authentication Configuration is stable as of Kubernetes 1.34. Both SPIFFE projects above carry a “Development Phase” badge and have single-digit stars — officially owned, not production-proven. Worth raising before anyone plans a customer demonstration on them.

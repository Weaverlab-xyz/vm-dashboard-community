{# Workload Lab → Kubernetes. A Password-Safe-brokered ServiceAccount token for a workload OUTSIDE the cluster. Backed by /api/workload-k8s. THIS IS THE MANAGED-CLUSTER ANSWER, and that is the whole reason it exists next to the SPIRE tab rather than inside it. The SPIRE lab's Kubernetes panel proves a workload can reach an API server holding a credential stored NOWHERE — but it does that with `--authentication-config`, a kube-apiserver flag, so it works on self-managed k3s and on none of EKS, AKS or GKE. Every cluster this dashboard provisions is in the second group. The two tabs are two answers to one question and the page shows both, because which one an operator can have depends entirely on who runs their control plane. Three things here are load-bearing and easy to mistake for decoration: * THE PROFILE, not the token. `deployer` binds ClusterRole/edit through a RoleBinding in ONE namespace; `reader` binds ClusterRole/view through a ClusterRoleBinding. Neither is cluster-admin, and the refusals are what the demonstration turns on. * `rotated`. A bearer token is far longer than the 128 characters Password Safe's create API accepts, so the managed account is ALWAYS created holding a placeholder. Until a rotation has completed the row looks onboarded and the vault holds nothing that authenticates — so the page says so rather than showing a green badge. * ROTATION DOES NOT REVOKE. A token already retrieved lives out its TTL. Deleting the ServiceAccount is the kill switch, because every token is bound to its uid. The consumer panel returns NO credential and never will: retrieval is the consumer's own Password Safe call with its own client id, which is what records WHICH BUILD read the token. A value proxied through this dashboard would record only that the dashboard did, and would be a second unaudited way to read it. #}

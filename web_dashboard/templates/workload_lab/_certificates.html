Builds a private CA — a GCP CAS DevOps-tier pool or an AWS Private CA — and onboards identities onto the Password Safe Certificate custom plugin family. Backed by /api/cert-lab. The cloud selector only appears when more than one module is built: it is filled from /api/cert-lab/options, which derives the list from the modules that actually exist rather than naming them here. TWO PACKAGES. The plugin ships as two .psplugin files over a shared core with different plugin ids, appearing in BeyondInsight as separate platforms with separate access control: "Certificate" issues an end-entity certificate, "Subordinate CA" issues an issuing authority that some other system (PRA Vault) holds and mints leaves beneath. An identity therefore carries a `package`, and the two are not a flag on one profile. Three things on this page are load-bearing and easy to mistake for decoration: * the address character counter. The managed system's Network Address is the ENTIRE configuration surface for this plugin (a Password Safe Cloud tenant cannot edit the appsettings.json inside the .psplugin) and Password Safe's column is 255 characters. The fully spelled-out ADCS profile from the plugin's documentation is 269 — and the subordinate topology is where the budget and the SAFETY CONTROL pull against each other, since a permitted-DNS list can exceed 100 characters on its own. * the path-length choice on the build form. A root created to issue leaves has a path length of zero and REFUSES to sign a subordinate at all — and it is the CA that refuses, with a policy error naming neither the flag nor this choice. It cannot be widened after the root exists, so it is a build question rather than a setting. * the cost line on each CA. The pool bills whether or not it ever issues anything, which is the entire reason this row has an auto-delete timer. #}

Password Safe as a certificate registrar and broker — it never becomes a certificate authority. The managed account holds the PKCS#12 passphrase, Secrets Safe holds the bundle it opens, and both halves are governed. Build a private CA here, onboard an identity onto it, then rotate from BeyondInsight. The plugin ships as two platforms: Certificate for an end-entity certificate, and Subordinate CA for an issuing authority another system mints beneath — a delegation of issuing authority rather than one more credential, which is why its access control is separate. A CAS pool, a self-signed root CA, and the enrollment service account the plugin authenticates as. Destroying it removes all three in one pass — the module sets the three flags CAS otherwise uses to refuse deletion.

A private CA, its self-signed root certificate, and the IAM user the plugin authenticates as. ~$400/month standing, twenty times the GCP pool, billed whether or not it issues anything — so it is refused outright unless auto-delete would stamp a timer on it.

The project id, not its display name or number. Defaults to the project this dashboard's GCP credential is scoped to; the pool lands wherever this says, so a different project needs the CA Service roles granted there too.

The pool, its CAs and any certificate template are all location-scoped and must agree.

A free-text field rather than a list: a Private CA is regional, and it is available in far more regions than CAS is.

Fixed when the root is created and not widenable afterwards. A root built to issue leaves has a path length of 0 and will refuse to sign a subordinate CA — and it is the certificate authority that refuses, with a policy error naming neither this choice nor the flag behind it. Pick can also sign a subordinate CA to demonstrate the Subordinate CA platform; it still issues end-entity certificates exactly as before.

One managed account per identity. The account name becomes the subject CN by default, and the whole profile below becomes the managed system's Network Address on the Certificate platform.

The managed credential here is an issuer, not a certificate. Password Safe obtains a subordinate CA from this root, something else — PRA Vault, typically — holds it and mints its own short-lived leaves beneath it, and Password Safe rotates the subordinate on a schedule. It lands on the Subordinate CA platform, whose access control is separate for that reason. Install the root chain into every target's trust store once, before anything else: that is what makes rotation safe, and nothing here automates it.

Rotation does not revoke. A target validates a leaf by walking its chain to the root and neither knows nor cares which subordinate was current when the leaf was minted — so this, not the rotation interval, is the exposure window if the signing key leaks. Issue it just longer than the interval Password Safe rotates it on: 8d against a 7-day schedule leaves two concurrently valid authorities briefly, where 1y would leave ~52.

A pipeline identity is not a host, so usually leave this empty — and note that under eku=Auto a DNS SAN drags serverAuth into the EKU set.

A vaulted CA key is not a credential to one system — it is the authority to mint an identity for anything the CA may assert. Constraints turn a compromise from mint anything into mint within a bounded namespace, and the extension is marked critical, so a relying party that cannot interpret it refuses the certificate rather than ignoring the boundary. Leaving this empty is allowed and warned about. Prefer the parent CA pool's own issuance policy where you can: the subordinate then inherits a boundary it cannot widen, and it costs nothing against the 255-character address.

A subtree is a network: 10.0.0.0/8, never 10.1.2.3/8. Host bits set is refused here, because no later action can detect a subordinate constrained to the wrong thing.

How many further CAs may appear beneath the subordinate. 0 is almost always right, and is all this lab's roots permit.

The Subordinate CA package already defaults to PemBundle, which is what a consumer of a CA key needs — PRA Vault's X.509 Parent Certificate Authority account takes a PEM key, a passphrase and a PEM certificate as three separate fields, and its key box says "Only PEM encoding is valid". Leaving this alone is both correct and 17 characters of address budget back.

No isca= and no bundle=: the Subordinate CA package already defaults both, and restating them would spend 27 characters of the budget the permitted-DNS list is competing for. No eku= either — the plugin asserts none on a CA certificate, because an EKU there constrains everything issued beneath it and implementations disagree about how.

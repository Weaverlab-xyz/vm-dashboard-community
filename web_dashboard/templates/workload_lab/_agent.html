{# Workload Lab → Agent. The non-human principal that CONSUMES what the other four tabs build. Backed by /api/agentcell. IT BELONGS HERE RATHER THAN ON A PAGE OF ITS OWN, and the reason is the whole point of the tab: every other tab on this page answers "how does a machine get a credential", and every one of them is answered in the abstract until something actually holds one. This tab is that something. It attests to the SPIRE tab's trust domain, and it can be made answerable for the Cloud tab's lease or the Kubernetes tab's token — so the four mechanisms stop being four demos and become one. FIVE THINGS HERE ARE LOAD-BEARING AND EASY TO MISTAKE FOR DECORATION: * IDENTITY AND AUTHORIZATION ARE TWO THINGS, and this tab must never draw them as one. The worker attests to SPIRE and gets an SVID — that is WHO IT IS, and it holds nothing. It calls /mcp with a Personal Access Token — that is WHAT IT MAY DO. Nothing mints one from the other (api/mcp_server takes a Bearer PAT and has no mTLS path), and the closing beat of the demo is exactly that gap: revoke the token and the worker is still who it was and may no longer do anything. * THE TOKEN IS SHOWN ONCE. Same contract as api/tokens.create_token — the row keeps the id, the name and the expiry, never the secret. The modal that shows it is therefore the only chance, and it says so. * A LINK IS NOT ALWAYS A CAPABILITY. `cloud` is accountability only, because that tab's credential is returned to nobody by design; `kubernetes` genuinely lets the worker request the token. Rendering the two alike is this feature's headline failure mode in one direction and the Kubernetes tab's in the other, so the picker states which it is BEFORE the link is made, not after. * THE DASHBOARD DOES NOT WATCH THE INSTALL. The two playbooks are runs the operator makes; nothing writes `stages_done`, so this tab shows the install as a checklist of what YOU do and names `journalctl -u mcp-agent` as the record. A progress bar here would be a field that is structurally always empty, which reads as "nothing happened yet" on a cell where plenty did. * REVOKE IS NOT UNINSTALL, and the confirm says so. The worker keeps running and keeps attesting; its next poll is refused. Hiding that behind a teardown would remove the only thing worth watching. #}

Two things, and nothing bridges them

Its identity is a SPIFFE SVID it re-attests on every loop, holding nothing at rest. Its authorization is a Personal Access Token bounded by the RBAC of the user you mint it against. The SVID does not authenticate to /mcp — closing that would need the Password Safe SPIFFE SVID plugin, whose configuration question is still unresolved. So the cell shows both halves and names the gap rather than implying a bridge.

That gap is the demo: revoke the token and the worker is still who it was, and may no longer do anything.

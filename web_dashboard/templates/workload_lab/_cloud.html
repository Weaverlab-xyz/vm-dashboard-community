{# Workload Lab → Cloud. A short-lived AWS/Azure credential for a workload, minted by Workload Credentials. Backed by /api/workload-cloud. THIS REPLACES THE MOST COMMON NON-HUMAN CREDENTIAL THERE IS. Ask how a build server reaches AWS and the answer is an access key in a CI secret store: no expiry, no revocation, no record of who read it. The other three tabs replace a certificate, a SPIFFE identity and a Kubernetes token; this one replaces that key. Three things here are load-bearing and easy to mistake for decoration: * THE SCOPE IS NOT SET HERE. The dynamic secret's definition in Workload Credentials decides which role is assumed and what it may do. This page NAMES the secret and cannot widen or narrow it — unlike the Kubernetes tab, which picks the RoleBinding itself. Saying so is the difference between a control surface and a claim. * REVOCATION IS ASYMMETRIC. Azure leases can be released early; AWS cannot, because STS will not withdraw a credential it has already signed. So on AWS the TTL is the only control there is, which makes a short one matter MORE there, not less. The page must never offer a Revoke button it cannot honour. * AN EXPIRED LEASE IS THE MECHANISM WORKING. `lease_state` is deliberately separate from `status`: a credential ageing out is the whole point, so it renders as a normal state and not as a fault. ISSUANCE IS METERED. Registering mints nothing, every Issue is one billed call, and the count is shown — a number climbing on an identity nobody is using is the signature of a consumer stuck in a retry loop. #}

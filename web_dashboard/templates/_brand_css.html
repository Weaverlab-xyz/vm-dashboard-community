{# The operator's own three colours, as real CSS. The shipped palettes in services/ui_theme are literal Tailwind utilities, because the app is on the Play CDN and a composed class name would not survive a build step that purges by scanning source. An arbitrary hex cannot be a utility at all, so a custom palette fills the same chrome slots with the hand-written class names below. They are not Tailwind classes: nothing purges them, and the class attribute in base.html that interpolates theme.nav_bg does not change. Two rules govern every edit to this file. 1. EVERY SELECTOR IS SCOPED to `.brand-custom`, which ui_theme puts on . A bare `.brand-nav` is specificity (0,1,0) -- a tie with any Tailwind utility on the same element setting the same property, and a tie is broken by source order, which for a sheet the CDN injects at runtime is script timing. The overlaps are real and deliberate: base.html:114 carries `text-white` beside theme.nav_bg, :161 and :260 carry `hover:text-white`, :260 carries `bg-white/10`, and login.html:77 and :136 carry `text-white` beside theme.login_btn. The descendant selector makes these (0,2,0) and the question never has to be asked. _checklist_styles.html's header states the same rule for the same reason. 2. VALUES COME FROM VARIABLES, NEVER FROM JINJA. The only interpolation in this file is the declaration list in :root, which ui_theme._custom_palette builds out of _mix/_text_on/_ink output and hexes that matched its ^#[0-9a-f]{6}$ check. That matters more here than anywhere else in the app: this is inside a {% endif %}

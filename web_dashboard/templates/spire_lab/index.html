Build a trust domain

A bare DNS-style name, not a spiffe:// URI. It is baked into the server config, every SPIFFE ID and the Managed System, and the plugin asserts it on every connect — so it cannot be changed afterwards.

No VM available. Deploy one from its cloud page first — the lab attaches to an existing host so it inherits that VM's SSH key, its auto-delete timer and its Destroy. Ubuntu 22.04 on the smallest shape that runs a Go binary is plenty. It must be on a subnet the Resource Broker can reach.

The functional account's name is this SPIFFE ID, not a username. It goes into the server's admin_ids — which is the line people get wrong: an entry-level -admin grants nothing to a minted SVID, and a missing admin_ids surfaces much later as PERMISSION_DENIED on Verify Functional Account.

What this will do, in order:

  1. Open tcp/ on the cloud ACL to — nothing, because no source CIDRs are configured
  2. Install SPIRE under systemd
  3. Open the host firewall on the same sources
  4. Seed registration entries ( should be discovered)
  5. Mint the administrative credential into Secrets Safe

Onboard into BeyondInsight

The dashboard does not write these objects. Whether BeyondInsight populates plugin attributes for an action has never been observed, and the plugin takes its whole configuration from them — so building a writer now would be betting on the answer. These are the values; §5 of the runbook is the order.

Trust bundle

Set SpiffeTrustBundlePem on the managed system to this. A SPIRE server presents only its leaf certificate, so there is nothing in the handshake to chain against and fingerprint pinning cannot substitute — without it every connect fails SPIRE Server certificate could not be validated. Public by construction: it is what every consumer of the trust domain has to trust.
